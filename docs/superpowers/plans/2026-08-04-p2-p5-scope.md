# P2–P5 Scope Plan

Date: 2026-08-04 · Status: **Scope only (not funded)** · Baseline: **`v1.0.0`** (P1 shipped)

## How to read this

This is a **roadmap-level scope** for the four paid phases in the SRS (§2, §4.7). It is not a
task-by-task build plan. Each phase gets a real task plan later, when the client funds it. Each
phase below states:

- **Goal** — what the phase delivers.
- **Requirements** — the SRS IDs it satisfies.
- **Schema delta** — the change against `internal/model/model.go` (the live P1 schema).
- **Architecture** — the new hexagonal packages and the ports they touch.
- **Decisions to settle** — the open design questions to answer before the build plan.
- **Depends on** — what must ship first.
- **Risk / effort** — a rough, relative estimate.

**Constraints for every phase** (same as the P1 plan):
- TDD, always. Failing test first.
- Hexagonal: new work goes in its own domain package behind a port; handlers are adapters.
- 15-Factor: config from env, logs to stdout, stateless process, DB as an attached service.
- PDPA: private fields (`phone`, `consent_*`, audit) never appear in a public response.
- Keep all data access portable through GORM. No SQLite-only feature (this keeps the P5
  Postgres move cheap). Today only two raw statements exist (backup `VACUUM INTO`, DSN `PRAGMA`s).

## Sequence

Build in SRS order: **P2 → P3 → P4 → P5**. The order is a dependency chain, not just a number line.

```
P2 approval + history ──> P3 year snapshots/locking ──> P4 bulk import ──> P5 district catalog + Postgres
        (moderation +          (uses P2 history to           (imports enter          (scale-triggered;
         revision log)          reconstruct a year)           P2 pending state)       needs a stable schema)
```

- **P2 is foundational.** Approval and edit history change the write path and the public read
  filter. Every later phase assumes they exist.
- **P3 uses P2.** A true year "snapshot" needs the revision log to reconstruct the state of a
  year at freeze time.
- **P4 uses P2 and P3.** Imported rows enter the P2 pending state; imports into a P3-locked year
  are refused.
- **P5 is last and scale-triggered** (NFR-ARCH-2: a measured performance need, not a date). Do the
  Postgres move only when the schema is stable, so the migration runs once.

## P2 — Approval before publish + edit history

**Goal.** A staff save no longer publishes at once. The save enters a **pending** state. The
central admin **approves** it before the public sees it. The system keeps a **full edit history**
(who, when, before, after) for every change. Approval and history ship together, because the
approval screen shows the before/after diff from the history.

**Requirements.** FR (SRS §4.7 P2). Extends FR-AUDIT-1 (last-writer audit) to a full trail.

**Schema delta.**
- Add a review state to `Doctor`, `Recipe`, and `Case`: a field such as
  `ReviewState string` with values `draft` / `pending` / `approved` / `rejected`. This is
  **separate** from `Doctor.Status` (active/inactive/deceased), which is content, not workflow.
- Add a generic **`Revision`** table: `id`, `entity_type`, `entity_id`, `changed_by`,
  `changed_at`, `action` (create/update/delete/approve/reject), `before_json`, `after_json`.
  One table serves all three entities.

**Architecture.**
- New `review` package (domain + port): the approval queue, and the approve/reject actions.
- New `revision` package (domain + port): write a revision row on every mutation.
- The write path in `doctor`, `recipe`, and `caserec` calls the revision port on each write,
  and sets `ReviewState = pending`.
- The **public read filter** in `publicapi` changes from `consent_obtained = true` to
  `consent_obtained = true AND review_state = approved`. Apply it on every public path (doctor,
  recipe, case), the same way the consent gate is applied today.

**Decisions to settle (the core P2 design question).**
1. **Edit to a live record.** When an editor changes an already-approved record, the public must
   keep seeing the **last approved version** until the admin approves the change. Two models:
   - **A. Status flag (simple).** One row per record + a `ReviewState`. A new record is hidden
     until approved. But an edit to a live record changes the live row — so the public sees the
     unapproved change, unless you also hide the record while it is pending. This has a gap.
   - **B. Pending shadow (correct, heavier).** Keep the approved version live and store the
     pending edit separately (a shadow row or a pending-revision). The public always reads the
     approved version. The admin approves to promote the shadow. This matches "approval before
     publish" for edits, but is more code.
   - **Recommendation:** Model B for correctness. Confirm with the client whether edits to live
     records need this, or whether only **new** records need approval (which makes Model A safe).
2. **Rejection.** Does reject delete the pending change, or return it to the editor as a draft?
3. **Delete.** Is a delete also queued for approval, or immediate for the admin only?

**Depends on.** P1 only.

**Risk / effort.** **High risk, large effort.** The shadow-version model and the read-filter
change touch every write and every public read. Get the model decision right first.

## P3 — Year snapshots and year locking

**Goal.** Freeze a whole `data_year` so old years become **read-only**. This protects a survey
year after it is closed.

**Requirements.** FR (SRS §4.7 P3). Builds on the year rule in the model spec §3.2.

**Schema delta.**
- Add a **`YearLock`** table: `data_year` (primary key), `locked_at`, `locked_by`.
- No column change to `Recipe`/`Case` is required; they already carry `DataYear`.

**Architecture.**
- New `yearlock` package (domain + port): lock a year, unlock a year, list locks.
- A **write guard** in the `recipe` and `caserec` write ports: refuse a create/update/delete when
  the row's `data_year` is locked. Return a clear error.
- The public read path does not change.

**Decisions to settle.**
1. **Snapshot vs lock.** "Snapshot" can mean two things:
   - **Lock only** — mark the year read-only and rely on the nightly backup for the frozen copy.
     Simple. No extra storage.
   - **True snapshot** — capture the exact state of the year at freeze time, for an immutable
     record. This needs the **P2 revision log** to reconstruct point-in-time state, or a copy of
     the year's rows into a snapshot store.
   - **Recommendation:** Start with **lock only**. Add a true snapshot if the client needs a
     citable frozen dataset per year.
2. **Doctor is not year-scoped.** A Doctor is one row per healer (model spec §3.2), with no
   `data_year`. Decide how a year lock affects Doctor edits — likely Doctor stays editable
   (it is not year data), and only Recipe/Case obey the lock. Confirm this with the client.
3. **Who locks.** Central admin only, per the access rules. Confirm.

**Depends on.** P2 (for true snapshots). Lock-only can ship without P2, but the SRS order keeps
P2 first.

**Risk / effort.** **Medium risk, medium effort.** Mostly a write guard and a small table. Effort
grows if the client wants true point-in-time snapshots.

## P4 — Bulk import of old paper/Excel data

**Goal.** Load the client's existing paper and Excel/Google-Form data into the app in bulk,
instead of re-typing it. The import maps to the same tables and obeys the same rules as manual
data entry.

**Requirements.** FR (SRS §4.7 P4).

**Schema delta.**
- No new entity is required; the import writes to existing tables through the existing repos.
- Optional **`ImportBatch`** table: `id`, `imported_by`, `imported_at`, `source_file`,
  `row_count`, `status`. It groups an import so the admin can review or undo one batch.

**Architecture.**
- New `importer` package — an **inbound adapter**. It parses Excel/CSV (reuse the `excelize`
  dependency already in P1), validates, and writes.
- **Reuse the existing domain services** (`doctor`, `recipe`, `caserec`, herb reconcile) for the
  writes, so the import inherits the same validation, audit, and code-linking rules. Do not write
  raw rows around the domain.
- Flow: **parse → validate (dry run) → report → commit in one transaction.**

**Decisions to settle.**
1. **Code linking (FR-LINK-1).** The import must link Recipe→Doctor and Case→Recipe by **code**,
   and flag a code/name mismatch, exactly like manual entry. Reuse the P1 `resolve-doctor` logic.
2. **Pending herbs.** An unknown herb name becomes a pending herb (FR-HERB-2), for the admin to
   reconcile after the import. Reuse the P1 pending-herb path.
3. **Review state (P2 link).** Do imported rows enter as **pending** (safe default, admin
   approves) or **approved** (trusted bulk load)? Recommend **pending**, with an admin option to
   bulk-approve a batch.
4. **Year lock (P3 link).** Refuse an import into a locked `data_year`.
5. **Consent.** Imported doctors default to `consent_obtained = false` (PDPA default), unless the
   source proves consent. Confirm.
6. **Idempotency.** A re-run must not duplicate rows. Match on `code`. Decide update-or-skip.

**Depends on.** P2 (for the pending state) and P3 (for the year-lock guard). It can ship without
them, but then it needs its own rules for the same questions.

**Risk / effort.** **Medium risk, medium–large effort.** The parsing is small; the **validation,
error reporting, and partial-failure handling** are the real work. A dirty source file is the main
risk. A dry-run report and a per-batch undo reduce it.

## P5 — District-managed herb catalog + Postgres migration

Two independent parts. Both belong to the "the app has outgrown one small VPS" phase.

### 5A — District-managed herb catalog

**Goal.** Let each **district** add and edit herbs in the catalog, instead of routing every new
herb through the central-admin reconcile queue. This removes the admin bottleneck as data grows.

**Requirements.** FR (SRS §4.7 P5). Changes the ownership rule in FR-HERB-1 (today: central admin
only) and the model spec §4.4.

**Schema delta.**
- The catalog stays **one shared province-wide list** (model spec §2), but write access widens.
- Add ownership/provenance to `Herb`: e.g. `created_by_district_id *uint`, so the admin can see
  who added a herb.
- Add a **merge/alias** mechanism for duplicates: a way to mark herb B as an alias of herb A and
  re-point B's ingredients to A. This is needed because widening write access re-introduces the
  duplicate-herb risk that the pending-herb reconcile removed.

**Architecture.**
- Extend the `herb` package: a `district_editor` may now create/edit a herb (a permission change
  in the herb write port). Keep the merge/de-dup action as a central-admin-only tool.
- The pending-herb path can stay as a fallback, or be retired once districts self-serve.

**Decisions to settle.**
1. **Shared or per-district catalog.** The SRS implies **one shared catalog** that districts
   co-edit. Confirm the client does not want separate per-district catalogs.
2. **Duplicate governance.** With open write access, two districts may add the same herb under
   different names. Decide the de-dup policy: admin merge tool, soft approval, or a name-match
   warning at save time. Recommend an admin **merge** tool plus a save-time near-duplicate warning.
3. **Edit rights.** May a district edit a herb another district created, or only add new ones?

**Depends on.** P1. Independent of P2/P3/P4, but do it after the schema settles.

**Risk / effort.** **Medium–high risk** (data governance, duplicates), **medium effort** on code.

### 5B — Move to PostgreSQL

**Goal.** Move the database from SQLite to PostgreSQL when a **measured** performance need arrives
(NFR-ARCH-2). This is triggered by scale, not a date.

**Requirements.** NFR-ARCH-2, NFR-PERF-1.

**Schema delta.** None in the model shape (GORM's dialect layer maps the types). The work is at
the driver and dialect level, not the entity level — which is why the P1 plan forbade SQLite-only
features.

**Architecture and work.**
- **Driver swap.** `github.com/glebarez/sqlite` → `gorm.io/driver/postgres` in `internal/db`.
  Note: the Postgres driver does **not** need cgo, so the binary can stay cgo-free.
- **Config (15-Factor).** Add a `DATABASE_URL` env var. The DB becomes an **attached backing
  service**, not an embedded file. This is more 15-Factor-correct, but it ends the "one process,
  no dependencies" property of NFR-ARCH-1 — the **main architectural cost** of P5.
- **The two raw statements.** The backup uses SQLite `VACUUM INTO`; replace it with a Postgres
  path (`pg_dump`, or a physical/base backup). The DSN `PRAGMA`s go away. Rewrite
  `docs/ops/restore.md`.
- **Data migration.** Move existing SQLite data to Postgres once (dump/transform/load). Verify
  row counts and the check constraints (e.g. `chk_herb_xor` in the `Ingredient` model).
- **Search and collation.** Review search behavior: `LIKE` vs `ILIKE`, and **Thai collation**, so
  keyword search stays correct on Thai text. This is the most likely behavior change.
- **Concurrency.** Real connection pooling replaces SQLite's single-writer model. Re-check the
  transaction code that P1 wrote to avoid the SQLite single-writer deadlock.
- **Deployment.** The prod image and the service install now need a Postgres instance. Update the
  Dockerfile/compose, the Windows MSI/service story, and the ops docs.

**Decisions to settle.**
1. **Trigger.** Define the measured signal that starts P5B (e.g. list > 1 s or search > 2 s at
   real counts, per NFR-PERF-1). Do not start it on a date.
2. **Managed or self-hosted Postgres.** A managed DB removes ops load but adds cost and a network
   dependency. Confirm with the client.
3. **Backup model.** Replace the nightly zip with a Postgres-native backup + the media directory.

**Depends on.** A stable schema — so run P5B **after** P2/P3/P4 land, to migrate once.

**Risk / effort.** **High risk, large effort.** The database move touches backup, deployment,
search, and concurrency at once. The GORM abstraction keeps the entity code stable, but the ops
and search work is real.

## Cross-cutting notes

- **Schema portability.** P2/P3/P4 add tables and columns. Keep them portable (no SQLite-only
  feature), so the P5B Postgres move stays a driver swap.
- **Public read filter.** P2 adds `review_state = approved` to the public filter. Keep the filter
  in one place, so P3/P4/P5 do not each re-implement it.
- **Audit and history.** P2's `revision` table is the base for P3 snapshots and the P4 import
  trail. Build it once, reuse it.
- **Every phase updates `CONTEXT.md` and ships its own task plan** under
  `docs/superpowers/plans/` before code, per the repo rules.

## Open questions for the client (before any phase is funded)

1. **P2:** Do edits to already-public records need approval (Model B), or only new records
   (Model A)?
2. **P3:** Lock-only, or true per-year snapshots? Does a year lock affect Doctor edits?
3. **P4:** What is the real source format (Excel, Google Forms export, paper only)? How clean is it?
4. **P5A:** One shared catalog co-edited by districts, or per-district catalogs?
5. **P5B:** What measured number triggers the Postgres move? Managed or self-hosted Postgres?
