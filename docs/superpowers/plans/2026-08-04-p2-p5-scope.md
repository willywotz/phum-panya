# P2–P5 Scope Plan

Date: 2026-08-04 · Status: **Scope + design decisions settled (not funded)** · Baseline: **`v1.0.0`**

## How to read this

This is an **engineering-readiness** scope for the paid phases in the SRS (§2, §4.7). The core
design decisions are **settled** (grilling session, 2026-08-04), so a task-by-task build plan can
start fast when a phase is funded. This document is not the build plan; each phase gets its own
TDD task plan under `docs/superpowers/plans/` before code.

Each phase states: **Goal**, **Requirements**, **Decisions (settled)**, **Schema delta** against
`internal/model/model.go`, and **Architecture** (the new hexagonal packages).

**Constraints for every phase** (same as the P1 plan):
- TDD, always. Failing test first.
- Hexagonal: new work goes in its own domain package behind a port; handlers are adapters.
- 15-Factor: config from env, logs to stdout, stateless process.
- PDPA: private fields (`phone`, `consent_*`, audit) never appear in a public response.
- Keep all data access portable through GORM — **no SQLite-only feature**. The Postgres migration
  is out of scope (see below), but this discipline is cheap insurance that keeps the option open.

## Sequence

Build in SRS order: **P2 → P3 → P4 → P5**. The order is a dependency chain.

```
P2 approval + history ──> P3 year locking ──> P4 bulk import ──> P5 district herb catalog
   (moderation +            (reconstructs a       (imports enter        (widen catalog
    revision log)            year from P2          P2 approved state,     write access)
                             history + backup)     obey P3 locks)
```

- **P2 is foundational.** Approval and edit history change the write path and the public read
  filter. Every later phase assumes they exist.
- **P3 uses P2.** A locked year is reconstructed point-in-time from the P2 revision log + backups.
- **P4 uses P2 and P3.** Imported rows enter the P2 approved state; imports into a P3-locked year
  are refused.
- **P5** widens herb-catalog write access. Independent of P2/P3/P4; do it after the schema settles.

## P2 — Approval before publish + edit history

**Goal.** A district-editor save no longer publishes at once. It enters a **pending** state. The
central admin **approves** it before the public sees it. The system keeps a **full edit history**
(who, when, before, after). Approval and history ship together — the approval screen reads the
before/after from the history.

**Requirements.** SRS §4.7 P2. Extends FR-AUDIT-1 (last-writer audit) to a full trail.

**Decisions (settled).**
1. **Gate scope — every change (Model B).** Every district-editor save goes `pending`. The public
   keeps seeing the **last-approved** version until the admin promotes the new one. (Chosen over
   "first-publication only": this is public medical content; an unreviewed dosage edit must not
   reach the public.)
2. **Granularity — per-record.** Each pending change is approved independently. Editing one Case
   queues only that Case. First-publishing a Doctor produces independent pending Doctor + Recipes
   + Cases, with an optional "approve all pending for this doctor" **bulk button** in the admin UI
   (a UI convenience, not a domain rule).
3. **Gate composition — consent and review are independent.** Public ⇔
   `consent_obtained AND review_state = approved`. Approval checks content quality only; it does
   **not** check consent. A Recipe/Case is public only if its **entire ancestor chain** is public
   (forced by attribution, FR-PUB-2).
4. **Pending storage — on-row.** The entity tables gain `review_state`
   (`pending`/`approved`/`rejected`), a `pending_json` overlay for edits, a `pending_delete` flag,
   and a `rejection_reason`. A **new** record is a real row with `review_state = pending` (filtered
   from public). An **edit** to an approved record leaves the real columns = approved (public keeps
   seeing them) and stashes the proposed change in `pending_json`; approve applies the overlay to
   the real columns. Rows always exist with stable ids/codes from creation, so a Recipe can attach
   to a not-yet-approved Doctor at once. (Chosen over a clean "live-table-always-approved" queue,
   which cannot give a pending new parent a real id for its children.)
5. **Whose writes queue — district editors only.** `district_editor` writes go pending;
   `central_admin` writes are **immediate** (auto-approved) — including admin edits, delete, and
   the PDPA erasure/unpublish (FR-DOC-3). The admin is the approver, so there is no one above to
   approve them.
6. **Reject — return to editor.** Reject sets `review_state = rejected` + a `rejection_reason`. The
   editor revises and resubmits; the pending-create row stays, a rejected edit keeps its overlay, a
   rejected delete clears the flag. The reject is logged as a revision event.
7. **Edit history — full snapshot per approved change.** An append-only **`Revision`** table stores
   one row per approved change: `entity_type`, `entity_id`, actor, timestamp, `action`
   (`create`/`update`/`delete`), and the full after-state as JSON. "Before" is the previous
   revision's snapshot; diffs are computed at display. Reject events are logged too.

**Schema delta.**
- On `Doctor`, `Recipe`, `Case`: add `ReviewState string`, `PendingJSON *string` (JSON),
  `PendingDelete bool`, `RejectionReason *string`. (`ReviewState` is separate from
  `Doctor.Status`, which is content — active/inactive/deceased — not workflow.)
- New `Revision` table: `id`, `entity_type`, `entity_id`, `changed_by`, `changed_at`, `action`,
  `after_json`.

**Architecture.**
- New `review` package (domain + port): the approval queue, and the approve/reject actions that
  promote or roll back the on-row pending state.
- New `revision` package (domain + port): append a revision row on every approved change.
- The write path in `doctor`, `recipe`, `caserec` branches on role: editor writes set the pending
  state; admin writes apply immediately and append a revision.
- The **public read filter** in `publicapi` adds `review_state = approved` on every public path
  (doctor, recipe, case), applied the same way the consent gate is applied today. Keep the filter
  in one place.

**Risk / effort.** **High risk, large effort.** The on-row pending model and the read-filter change
touch every write and every public read.

## P3 — Year locking

**Goal.** Freeze a whole `data_year` so its records become **read-only**. This protects a survey
year after it is closed.

**Requirements.** SRS §4.7 P3. Builds on the year rule in the data spec §3.2.

**Decisions (settled).**
1. **Lock-only, no materialized snapshot.** A `YearLock` row marks a `data_year` read-only. Writes
   to that year's Recipe/Case are refused. Point-in-time state, if ever needed, is reconstructed
   from the **P2 `Revision` trail + the nightly backup** — no copied data. (A true materialized
   snapshot is added later only if the client needs a citable annual published/exported volume.)
2. **Scope — Recipe/Case only; Doctor exempt.** Locking year Y freezes only Recipe/Case rows with
   `data_year = Y`. A Doctor profile stays editable (status → deceased, consent withdrawal, fixes)
   and can still gain records in later unlocked years (the year-model intent). Riders:
   - **PDPA erasure/unpublish overrides any lock** — a healer opt-out must delete their locked-year
     records too; the law outranks the freeze.
   - A year can be **locked only when its pending queue is empty**, so "locked" always means "final
     approved state."

**Schema delta.**
- New `YearLock` table: `data_year` (primary key), `locked_at`, `locked_by`.
- No column change to `Recipe`/`Case` (they already carry `DataYear`).

**Architecture.**
- New `yearlock` package (domain + port): lock a year, unlock a year, list locks (central admin).
- A **write guard** in the `recipe` and `caserec` write ports: refuse create/update/delete when the
  row's `data_year` is locked, except the admin-erasure path. The public read path is unchanged.

**Risk / effort.** **Medium risk, medium effort.** A small table + a write guard.

## P4 — Bulk import (canonical template)

**Goal.** Load the client's existing paper/Excel data in bulk instead of re-typing it, through the
same tables and rules as manual data entry.

**Requirements.** SRS §4.7 P4.

**Decisions (settled).**
1. **Canonical Excel template — not an arbitrary-source adapter.** Publish one Excel template that
   is the spreadsheet twin of the standard form Sheets A/B/C (data spec §5) — columns = our fields,
   links by `code`. Old paper/Google-Form data is **transcribed into the template** (client-owned
   data entry). The importer parses this one known shape only. (The paper form already maps 1:1 to
   the data model, so the importer stands on it instead of re-solving column mapping per source.)
2. **Imported rows = `approved` on import, consent-gated.** The import is an admin action, so rows
   are approved immediately (consistent with P2 "admin writes are immediate"). Nothing floods the
   public: imported Doctors default to `consent_obtained = false` and stay hidden until consent is
   recorded per healer. Import **quality** is caught by a **dry-run validation report**, not by an
   approval queue.
3. **Insert-only — skip + report duplicates.** An import batch only *adds* new records. Any `code`
   that already exists is **skipped and listed in the report** — never overwritten. Re-running the
   same file is idempotent. Corrections to already-imported data go through the **normal edit UI**
   (which carries P2 history + approval). Consequences:
   - Write **through the domain services** (`doctor`/`recipe`/`caserec`/herb reconcile), so the
     import inherits validation, audit, code-linking (FR-LINK-1), and the pending-herb path
     (FR-HERB-2). Do not write raw rows around the domain.
   - **Refuse an import into a P3-locked year.**
   - **Per-batch undo** via an `ImportBatch` row that groups the insert.

**Schema delta.**
- New `ImportBatch` table: `id`, `imported_by`, `imported_at`, `source_file`, `row_count`,
  `status`. Tag each imported row's batch for review/undo.
- No new entity for the data itself; the import writes to existing tables.

**Architecture.**
- New `importer` package — an **inbound adapter**: parse the template (reuse `excelize`) →
  validate (dry run) → report → commit in one transaction, reusing the domain services.

**Risk / effort.** **Medium risk, medium effort.** Parsing is small; **validation, error reporting,
and partial-failure handling** are the work. A dry-run report + per-batch undo contain the risk.

## P5 — District-managed herb catalog

**Goal.** Let each **district** add and edit herbs in the catalog, instead of routing every new
herb through the central-admin reconcile queue. This removes the admin bottleneck as data grows.

**Requirements.** SRS §4.7 P5 (herb-catalog part only; the Postgres migration is **out of scope** —
see below). Changes the ownership rule in FR-HERB-1 and data spec §4.4.

**Decisions (settled).**
1. **One shared province-wide catalog — districts get write access.** The catalog stays a single
   shared list (**forced by FR-SEARCH-2**: the public filters recipes by one herb from the shared
   catalog; per-district catalogs would fragment the same herb and break cross-district filtering).
   "District-managed" means write access widens, not that each district gets its own catalog.
2. **Governance — add + edit-own + admin-merge.** A district may **add** new herbs and **edit the
   ones it created**; only the central admin edits across districts and runs a **merge/alias** tool
   (mark herb B an alias of A and re-point B's ingredients to A). A **save-time near-duplicate
   warning** nudges against dupes. This keeps districts unblocked (the P5 goal) while containing the
   blast radius and giving the admin a cleanup path. The P1 pending-herb path stays as an optional
   fallback.

**Schema delta.**
- On `Herb`: add provenance, e.g. `created_by_district_id *uint`, and an alias link, e.g.
  `alias_of_id *uint` (a herb marked as an alias points to its canonical herb).
- A merge action re-points `Ingredient.HerbID` from the alias to the canonical herb.

**Architecture.**
- Extend the `herb` package: widen the write port so a `district_editor` may create a herb and edit
  its own; keep the merge/alias action central-admin-only. Add a near-duplicate check at save.

**Risk / effort.** **Medium risk, medium effort.** The risk is data governance (duplicates), not
code volume; the merge tool + near-dup warning address it.

## Out of scope

- **SQLite → PostgreSQL migration (was SRS P5 / NFR-ARCH-2).** Explicitly **out of scope** by a
  2026-08-04 scoping decision. The app stays on SQLite. This overrides the SRS's performance-
  triggered P5 framing. **Re-scope trigger:** if, at real counts under normal load, a list page
  sustains **> 1 s** or a search sustains **> 2 s** (NFR-PERF-1), *or* SQLite write-lock contention
  appears (`SQLITE_BUSY` with concurrent writers), reopen this as its own phase. If reopened, the
  provisional shape is **managed Postgres** (offloads DB ops the non-IT owner cannot carry), with:
  `DATABASE_URL` as a 15-Factor attached service; replace the `VACUUM INTO` backup with `pg_dump`
  and rewrite `docs/ops/restore.md`; review Thai collation / `ILIKE` search; recheck transactions
  and connection pooling; swap `glebarez/sqlite` → `gorm.io/driver/postgres` (still cgo-free);
  one-time data migration. Until the trigger fires, keep the GORM portability discipline so this
  stays a driver swap.
- Per SRS §2: nothing beyond the phases above. Off-site/DR backup beyond the nightly local zip is
  the owner's job.

## Cross-cutting notes

- **Public read filter** lives in one place (`publicapi`). P2 adds `review_state = approved`; P3/P4
  do not re-implement it.
- **`Revision` table (P2)** is the base for P3 point-in-time reconstruction and the P4 import trail.
  Build it once, reuse it.
- **Every phase updates `CONTEXT.md` and ships its own TDD task plan** before code, per repo rules.
- **ADRs at funding time** (not now — nothing is being built): P2's on-row-pending / Model-B design,
  and — only if the migration is ever re-scoped — a Postgres ADR extending ADR-0001.
