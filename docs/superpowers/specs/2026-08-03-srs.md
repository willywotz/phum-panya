# Software Requirements Specification — Folk-Medicine Web App (phum-panya)

Date: 2026-08-03
Status: Approved (design phase)
Audience: the builder. Language: English (Simplified Technical English).

## 1. Purpose and scope

This document tells a builder what to build and how to verify it. It is the
engineering spec for a web app that collects folk-medicine records
(ตำรายาหมอพื้นบ้าน) for one province, grouped by district (อำเภอ). The public
reads all data. One editor per district plus a central admin write the data.
Access is by QR scan to a browser. There is no app-store app and no map.

This SRS does not repeat the data model. The data model, field list, access
rules, and paper form are in the approved design:
`docs/superpowers/specs/2026-08-03-data-model-and-form-design.md` (referenced
below as "the model spec"). The stack decision is in
`docs/adr/0001-single-go-binary-embedded-nextjs.md`.

## 2. Phases

The SRS covers all phases. Every functional requirement carries a phase tag.
The builder reads P1 as the first-build backlog.

| Phase | Contents | Funding |
|---|---|---|
| **P1 — Launch** | Staff CRUD (Doctor/Recipe/Case); user management; public read with search and filter; central herb catalog; pending-herb; consent and PDPA fields with opt-out; audit fields; bilingual UI; print/PDF page; staff bulk export; local backup | Funded |
| **P2** | Approval-before-publish and edit history (they travel together) | Paid, later |
| **P3** | Year snapshots and year locking | Paid, later |
| **P4** | Bulk import of old paper/Excel data | Paid, later |
| **P5** | District-managed herb catalog; move to PostgreSQL / server migration | Paid, later |

In P1 a staff save publishes at once. There is no review step until P2.

## 3. Actors

| Actor | Access |
|---|---|
| **Public** | Reads all public data. No login. |
| **District editor** | Logs in. Writes only the Doctors, Recipes, and Cases of the editor's own district. |
| **Central admin** | Logs in. Writes all districts. Manages Users, the District list, and the shared Herb catalog. |

Access rules are in the model spec §3. Private fields (`phone`, `consent_*`,
audit fields) are never in a public response.

## 4. Functional requirements

Each requirement has an ID, a phase tag, and an acceptance criterion in
Given/When/Then form. The builder writes the failing test first (TDD).

### 4.1 Authentication and users

**FR-AUTH-1 (P1) — Session login.**
Staff log in with email and password. The server sets a session cookie.
- *Given* a valid email and password of an active user, *when* they submit the
  login form, *then* a session starts and the user reaches the staff area.
- *Given* a wrong password, *when* they submit, *then* login fails with no hint
  about which field was wrong.

**FR-AUTH-2 (P1) — Logout.**
- *Given* a logged-in user, *when* they log out, *then* the session ends and
  staff pages are no longer reachable.

**FR-AUTH-3 (P1) — Login throttling.**
- *Given* repeated failed logins for one account or IP, *when* a threshold is
  passed, *then* further attempts are blocked for a cool-down time.

**FR-USER-1 (P1) — Central admin manages users.**
The central admin creates, edits, and deactivates users, sets the role
(`central_admin` or `district_editor`), and assigns a district to an editor.
- *Given* the central admin, *when* they deactivate a user, *then* that user
  can no longer log in.

**FR-USER-2 (P1) — Admin-managed password reset.**
The central admin resets any user's password. There is no self-service reset
and no email in P1.
- *Given* the central admin sets a new password for a user, *when* that user
  logs in with it, *then* login succeeds.

### 4.2 District and herb catalog

**FR-DIST-1 (P1) — Central admin manages districts.**
The District list is a fixed list the central admin owns.

**FR-HERB-1 (P1) — Central admin manages the herb catalog.**
The shared Herb catalog is province-wide. Only the central admin adds or edits
herbs (fields in the model spec §4.4). District-managed catalog editing is P5.

**FR-HERB-2 (P1) — Pending herb.**
When a district editor names a herb that is not in the catalog, the editor
saves it as a pending herb on the ingredient row. The recipe saves at once.
- *Given* an ingredient with a herb name not in the catalog, *when* the editor
  saves, *then* the recipe saves with a `pending_herb_name` and no catalog link.

**FR-HERB-3 (P1) — Central admin reconciles pending herbs.**
The central admin sees pending-herb names and either links each to a catalog
herb or adds a new herb.
- *Given* a pending herb, *when* the admin links it to a catalog herb, *then*
  the ingredient points to that herb and the pending name is cleared.

### 4.3 Doctor, Recipe, Case (staff CRUD)

**FR-DOC-1 (P1) — District editor CRUD for own district.**
A district editor creates, reads, updates, and deletes Doctors of the editor's
own district (fields in the model spec §4.3).
- *Given* a district editor, *when* they try to edit a Doctor of another
  district, *then* the app refuses.

**FR-DOC-2 (P1) — Consent gate before public.**
A Doctor is public only when `consent_obtained` is yes.
- *Given* a Doctor with `consent_obtained` = no, *when* the public views the
  site, *then* that Doctor and its Recipes and Cases are not shown.

**FR-DOC-3 (P1) — Right to erasure.**
The central admin unpublishes or deletes a Doctor and its Recipes and Cases on
a healer's opt-out request (model spec §3.1).

**FR-REC-1 (P1) — Recipe CRUD with ingredients.**
A district editor creates, edits, and deletes Recipes of the editor's own
district, each with an ingredient list (herb or pending herb, amount, unit,
note). Recipe links to its Doctor by code (model spec §5).

**FR-CASE-1 (P1) — Case CRUD, anonymous.**
A district editor creates, edits, and deletes Cases. A Case links to one Recipe
by code. A Case holds no patient name or ID (model spec §4.7).

**FR-LINK-1 (P1) — Code linking with mismatch flag.**
Records link by code, not name. If a form's code and its double-check name
disagree at data entry, the row is flagged for the central admin (model spec
§5 "How the sheets connect").

**FR-AUDIT-1 (P1) — Audit fields on every write.**
Every write records `updated_by` and `updated_at`. Full edit history is P2.

### 4.4 Public read

**FR-PUB-1 (P1) — Public reads Doctors, Recipes, Cases.**
The public reads all consented Doctors and their public Recipes and Cases. No
login. Private fields are never shown.

**FR-PUB-2 (P1) — Attribution.**
Every public Recipe credits its Doctor by name and district (model spec §3.1).

**FR-SEARCH-1 (P1) — Keyword search and district filter.**
The public Doctor list and the public Recipe+Case list each support a keyword
search and a district filter.
- *Given* a keyword that matches a public Doctor, *when* the public searches,
  *then* that Doctor appears in the result.

**FR-SEARCH-2 (P1) — Filter recipes by herb.**
The public filters recipes by one herb from the shared catalog.

### 4.5 Print and export

**FR-PRINT-1 (P1) — Print/PDF healer page.**
Each public healer page has a print-friendly view (print stylesheet) that the
public prints or saves as PDF from the browser. It shows public fields only.

**FR-EXPORT-1 (P1) — Staff bulk export.**
Staff export data as Excel/CSV. A central admin exports all districts; a
district editor exports the editor's own district only. The public has no bulk
export.
- *Given* a district editor, *when* they export, *then* the file holds only the
  editor's district and no private fields (`phone`, `consent_*`, audit).

### 4.6 Backup

**FR-BACKUP-1 (P1) — Nightly backup.**
A scheduled nightly job writes one zip that holds the SQLite database file and
the images directory, to a second location on the same server, and keeps the
last N days.

**FR-BACKUP-2 (P1) — Restore docs.**
A one-page, tested restore procedure ships with P1. Off-site copies are the
owner's job (state this boundary in the docs).

### 4.7 Later phases (named, specified when funded)

- **P2** — Approval-before-publish: a staff save enters a pending state; the
  central admin approves before it goes public. Edit history records each change
  (who, when, before/after).
- **P3** — Year snapshots and year locking: freeze a whole `data_year` so old
  years are read-only.
- **P4** — Bulk import of old paper/Excel data.
- **P5** — District-managed herb catalog; move the database to PostgreSQL as a
  server migration.

## 5. Non-functional requirements

### 5.1 Architecture and deployment

**NFR-ARCH-1** — The app is one Go binary that serves a JSON API and the
embedded Next.js static export (ADR-0001). The runtime is a single process.

**NFR-ARCH-2** — The database is SQLite in P1. The data-access layer uses
standard SQL portable to PostgreSQL; no SQLite-only features. The move to
PostgreSQL (P5) is triggered by a measured performance need, not a date.

**NFR-DEPLOY-1** — The Go binary terminates TLS on port 443 with built-in ACME
(Let's Encrypt) and auto-renews. No reverse proxy is required. The server must
be reachable on ports 80 and 443.

**Client dependency** — The client provides a domain name that points to the
server. TLS and QR both need it.

### 5.2 Platform and UI

**NFR-UI-1** — The site is responsive and works on current mobile and desktop
browsers. Entry is by QR to an `https://` URL. No app-store app.

**NFR-I18N-1 (P1)** — The UI is bilingual. Thai is the default; an English
toggle switches UI labels, buttons, menus, and messages. User-entered record
content (names, texts, local herb names) is never translated.

**NFR-A11Y-1** — Best-effort WCAG 2.1 AA basics: semantic HTML, image alt text,
sufficient colour contrast, keyboard-navigable forms, readable font sizes. This
is a design guideline, not a pass/fail gate.

### 5.3 Images

**NFR-IMG-1** — On upload the server re-encodes and downscales each image
(long side capped, JPEG/WebP), and strips EXIF (this also removes GPS, so a case
photo cannot leak patient location). There is no input file-size limit; the
server streams an upload to a temp file, not to memory.

**NFR-IMG-2** — Processed images are stored on the filesystem; the database row
holds the path only. The central admin sees current storage use against the
~30 GB server ceiling.

### 5.4 Scale and performance

**NFR-SCALE-1** — Design to these order-of-magnitude figures (no real counts
yet): ~10–25 districts, ~15–30 staff, ~500 doctors, ~3–5k recipes, low-thousands
cases, 1–3 concurrent writers, tens of concurrent public readers.

**NFR-PERF-1** — On the ~350 THB VPS at ~5k records: a list page returns in
under 1 s and a search returns in under 2 s under normal load. These targets are
provisional until real counts arrive.

### 5.5 Availability and recovery

**NFR-AVAIL-1** — Best-effort availability on a single server. No SLA. Short
maintenance windows are acceptable.

**NFR-DR-1** — Recovery is from the nightly backup. RPO = the last nightly zip.
RTO = the time to restore the zip and redeploy the binary.

### 5.6 Security and PDPA

Thai PDPA applies. The site names real healers and publishes their knowledge.

**NFR-SEC-1** — All traffic is HTTPS/TLS. No plaintext login.

**NFR-SEC-2** — Passwords are hashed with a modern KDF (argon2 or bcrypt). A
password is never logged or returned.

**NFR-SEC-3** — Login is throttled/locked after repeated failures (see
FR-AUTH-3).

**NFR-SEC-4** — Private fields (`phone`, `consent_*`, audit fields) are never in
any public page or API payload.

**NFR-SEC-5** — Consent gate before public (FR-DOC-2) and right to erasure
(FR-DOC-3) are enforced.

**NFR-SEC-6** — Standard web hardening: parameterized queries, output escaping,
CSRF protection on the session cookie, safe upload handling (NFR-IMG-1). Case
photos are EXIF-stripped and must be face-free (model spec §3.1).

## 6. Verification and acceptance

**Two layers.**

1. **Automated tests (primary evidence).** Each functional requirement has a
   testable acceptance criterion (§4). The builder writes the failing test
   first, then the code (repo TDD rule).
2. **Client UAT checklist (acceptance gate).** The client runs a short checklist
   to sign off P1. It ties to the "2 revision rounds + 90-day free bugfix" terms
   from the client chat.

### 6.1 P1 UAT checklist (draft)

1. Central admin creates a district editor and assigns a district.
2. The editor logs in and creates a Doctor with a photo.
3. The Doctor is not public until consent is ticked.
4. The editor adds a Recipe with one catalog herb and one pending herb; it
   saves.
5. The central admin reconciles the pending herb.
6. The editor adds an anonymous Case linked to the Recipe.
7. The public finds the Doctor by keyword and by district filter.
8. The public filters recipes by one herb.
9. The public prints/saves the healer page as PDF (public fields only).
10. A district editor exports own-district data; the file has no private fields.
11. The nightly backup zip contains the database and images; a restore from it
    succeeds per the restore docs.
12. The UI switches Thai/English labels; record content stays as typed.

## 7. Out of scope for P1

Everything in phases P2–P5 (§4.7): approval-before-publish, edit history, year
snapshots/locking, bulk import, district-managed herb catalog, and the move to
PostgreSQL. Off-site/DR backup beyond the nightly local zip is the owner's job.
